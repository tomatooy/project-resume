# VS:Résumé browser extension

The independent Chrome app is `apps/extension`. It uses the existing web Worker at `/api/v1`; it does not need an open app tab. Shared browser-safe oRPC contracts and the client live in `packages/api`.

## Configure and load

1. Copy `apps/extension/.env.example` to `apps/extension/.env.local` for development. Copy `apps/extension/.env.production.example` to `apps/extension/.env.production.local` for production. Set `VITE_APP_ORIGIN`, `VITE_SUPABASE_URL`, and `VITE_SUPABASE_PUBLISHABLE_KEY` in each file. The origin identifies the main app's backend. Production builds require hosted HTTPS URLs.
2. Run `bun install --frozen-lockfile`, then `bun run build:extension:dev` for an unpacked local build or `bun run build:extension` for production. `bun run dev:extension` watches in development mode; it does not start the web app. Both modes write to `apps/extension/dist`, so rebuild and reload the extension when switching.
3. In Chrome 127 or newer, open `chrome://extensions`, enable Developer mode, select **Load unpacked**, and choose `apps/extension/dist`.
4. Record the extension ID shown by Chrome. For a stable development/release identity, set `VITE_EXTENSION_PUBLIC_KEY` in the corresponding environment file to the extension's public key and rebuild. Never put a private signing key in this variable.
5. Add the exact callback `https://<extension-id>.chromiumapp.org/auth/callback` to the Supabase Auth redirect allowlist. The extension uses a separate Google PKCE session; it does not copy the app's session or refresh token. Add each development and production ID explicitly.
6. Configure the existing web Worker with `EXTENSION_ORIGINS=chrome-extension://<extension-id>` (comma-separated for multiple exact IDs). For local development this belongs in `apps/web/.dev.vars`; production belongs in `vars.EXTENSION_ORIGINS` in `apps/web/wrangler.jsonc`. The production allowlist starts empty until the release ID is known. Its public Supabase configuration must identify the same project as the extension.
7. Configure `TAILOR_ENCRYPTION_KEY_V1` as a Worker secret and in `.dev.vars` locally. Use a random 32-byte key encoded as base64. Keep it for the lifetime of in-flight attempts. Neither this secret nor a model key belongs in the extension.
8. Apply the `20260924*` database migrations through the normal environment migration process, including the Realtime publication for job bindings and tailoring operations. The `TAILOR_WORKFLOW` binding in `apps/web/wrangler.jsonc` names `resume-tailoring`, class `TailorWorkflow`, exported from `src/server.ts`. Deploy the compatible backend before distributing the extension.

The production backend is `https://vs-resume.ouyangzongxin.workers.dev`, using the Supabase project `gbwyxuqprtumutqmluju`. The release extension ID and public key still need to be supplied. Follow the [deployment checklist](../deployment.md) before distributing a production extension build.

## OAuth returns to the main app

If the OAuth window stays open on the main app and the extension still shows **Connect account**, check the Supabase redirect allowlist. Replace `<extension-id>` with the actual ID from `chrome://extensions`; it must match the ID in `EXTENSION_ORIGINS`. For local Supabase, update `additional_redirect_urls` in `supabase/config.toml`, then run `bun run --filter @workspace/supabase stop` and `bun run --filter @workspace/supabase dev` to apply it. Close the old OAuth window and start a new connection from the panel.

Successful authentication returns to `https://<extension-id>.chromiumapp.org/auth/callback`, closes the OAuth window, and persists a separate extension session in `chrome.storage.local`. Main-app cookies do not connect the extension. **No job or application detected** only means the tab is not a supported job or application page; the account email in the panel footer indicates a connected account.

## Tailoring fails before generation

If a saved attempt has `error_class=dispatch_failed`, check the Worker encryption configuration before retrying. `TAILOR_ENCRYPTION_KEY_V1` must be base64 encoding of exactly 32 random bytes, not a 32-character passphrase or 33 decoded bytes. Generate it with `openssl rand -base64 32` and store it only in `apps/web/.dev.vars` locally or the production Worker secret. Keep an existing valid key while attempts are in flight.

After changing `.dev.vars`, restart the local web dev process so the Worker uses the new value. Retry the failed attempt from the extension using its saved description. Configuration validation now runs before admission or retry, logs `tailoring.configuration` with a fixed error class, and does not create another attempt or consume quota. `shared_api` / `jobs.lookup` info lines only measure status reads; they do not describe a generation failure.

## Behavior and boundaries

Page classification follows the top-level URL and live ATS frames. The design and its edge cases are in `docs/superpowers/specs/2026-10-17-extension-panel-states-design.md`.

- **Job pages** use HTTPS on `www.linkedin.com`: `/jobs/search-results` (trailing slash optional) with a query, or `/jobs/view/<numeric-id>` including slugged view paths. IDs have at least six digits. A view/query disagreement is rejected. A search page without a selected ID asks the user to select a job.
- **Application pages** are HTTPS pages, on the default port, of a known applicant tracking system: Workday (`*.myworkdayjobs.com`, `*.myworkdaysite.com`), Greenhouse (`boards.greenhouse.io`, `job-boards.greenhouse.io`, and their `eu.` forms), Lever (`jobs.lever.co`, `jobs.eu.lever.co`), Ashby (`jobs.ashbyhq.com`), SmartRecruiters (`jobs.smartrecruiters.com`, `careers.smartrecruiters.com`), and iCIMS (`*.icims.com` except `www.icims.com`). Wildcard hosts need a subdomain. The list lives in `apps/extension/src/lib/pages.ts`; the manifest's host permissions and the widget host's matches must equal it, and the autofill script's matches must equal its Greenhouse, Ashby, and Lever hosts (`AUTOFILL_MATCHES`). Tests check both.
- **Embedded applications** are company pages containing a live Greenhouse, Ashby, or Lever frame. Chrome's frame URLs identify the vendor; query parameters, script tags, and iframe IDs alone do not establish support. The toolbar shows an **ATS** badge. Click it to mount the panel on the company page using the existing `activeTab` permission.
- **Unsupported pages** are everything else, including other LinkedIn pages without a supported application frame.

Job pages and hosted ATS pages open the isolated in-page panel, docked to the right, without taking focus. Company pages require a toolbar click to mount the host. Its header can minimize it to a compact widget pinned to the right edge, or close it for the tab. Hover or keyboard focus on the widget reveals the drag handle and close button. Drag vertically, or use the handle’s arrow keys, to move it; the extension remembers its relative position across tabs and clamps it to the viewport. Clicking the widget reopens the panel. Each tab keeps one mode for job pages and one for application pages, so after closing the panel on one job, later jobs in that tab stay closed while new tabs open it again. The modes last until the tab closes, the browser restarts, or the extension reloads or updates. Disconnecting the account does not reset them.

On unsupported pages nothing appears until the toolbar icon is clicked. The panel then stays on that page, including query and hash changes, and goes away once the page changes or reloads. On any page the toolbar icon closes a showing panel and otherwise opens one. Where Chrome does not let extensions run, such as `chrome://` pages and the Chrome Web Store, the click shows nothing and the icon's tooltip reads "VS:Résumé can't run on this page" until the tab loads another page.

Every panel first checks the account and offers **Connect account** when none is connected. Job pages then show resume tailoring. Greenhouse, Ashby, and Lever application pages show Autofill (see Autofill below); other application pages show a placeholder naming the detected system. Unsupported pages say **No job or application detected** and offer **Open VS:Résumé**. The panel owns its header and has no browser pin/unpin controls. Its surface is light, its header text is gray, and the floating widget uses the shared grayscale palette.

A tab opened in the background loads its panel when first shown. Installing or updating the extension adds the host to open job and hosted ATS tabs and the autofill script to matching Greenhouse, Ashby, and Lever frames, including embeds on company pages. The toolbar also repairs a missing autofill script. A host left behind by the previous version removes itself, so open tabs need no refresh. If a page replaces its document during hydration, the panel host remounts and autofill keeps watching the new form. Pages restored from the back/forward cache refresh the host and the panel.

On **Tailor resume**, the extension fetches the selected posting through authenticated `POST /api/v1/jobs/linkedin/{externalJobId}/posting`. This calls the same `TailorService.fetchPosting` and `WorkerJobFetcher` as the web app, including canonical LinkedIn URLs, the ten-second request timeout, HTML-to-text conversion, and text limits. The widget host content script hosts the isolated widget or panel frame and checks embedded-frame visibility; it never reads job descriptions or account data. `activeTab` and `scripting` let the toolbar add that host to the current page. Before submitting, it rechecks the active tab, selected job, returned posting URL, and account. Existing bindings skip fetching; retries reuse the saved description. Rebuild and reload the extension after updating the backend to use this endpoint.

Above **Tailor resume**, an optional **Additional instructions** box (up to 4,000 characters) steers the generation, for example "Don't include a summary". The panel saves the text per account in this browser's `chrome.storage.local` as it is typed, and sends it with **Tailor resume**. Admission stores it on the tailoring operation (`tailor_operations.instructions`), where the workflow reads it. The prompt follows it over the default tailoring preferences, but never over factual integrity, keeping every job, or the output schema.

The panel reads persisted status on opening and focus. While open on a supported job, the service worker subscribes to RLS-scoped Supabase Realtime changes for that job's binding and current operation, then tells the panel to fetch a fresh snapshot. A disconnected subscription falls back to a ten-second check. The panel keeps its current content visible during refresh. Transport errors remain distinct from generation failure. API calls and account storage are restricted to the service worker; only an exact extension panel sender can invoke privileged messages. An embedded panel is trusted only while its tab shows the panel for the current page, and its snapshots, subscriptions, and URL-change refreshes stay bound to that tab. Supabase storage is restricted to trusted extension contexts. Last-base preferences and ambiguous-request keys are account-scoped.

The database owns `(user, platform, job)` uniqueness. Admission clones the source and snapshots it before parsing. Initial admission, retries, and all other agent runs share atomic hourly quota accounting. Each retry snapshots the current saved copy, preserves its ID, and reuses the stored job text. Generated output is staged under owner RLS. Success writes the head and immutable version only after checking the current attempt, deadline, deletion, and revision under a lock. Cancellation fences commits before best-effort workflow termination.

Ordinary assistant changes still require accepted patches. Explicit extension **Tailor resume** and **Retry** authorize this specific whole-document creation/recovery operation. They do not grant the chat assistant general write authority.

Workflows receive only an AES-GCM encrypted, operation-bound envelope containing a short-lived user access token. There is no background refresh token or service-role client. Attempts last five minutes and require a further minute of token validity. Model calls have a maximum 120-second deadline-aware signal and one SDK retry; workflow step retries are bounded and recheck the overall deadline. Checkpoint results contain only operation IDs. Staged content is purged on terminal transition. Fresh authenticated reads reconcile expired work if the workflow can no longer authenticate. An ambiguous dispatch retains the admission and reuses its workflow instance ID.

Legacy target identity is backfilled lazily under the caller's RLS credentials using the shared URL parser. Captures and associations are preserved. Lookup pins the newest live origin association, with stable ID tie-breaking, and only infers readiness from a completed tailoring run with a persisted version. A soft-deleted binding does not fall back to an older resume. Legacy synchronous runs are never dispatched as new workflow instances. Their existing request still performs the model work; its final write now shares the atomic cancellation and revision guards so adoption cannot let a late writer bypass cancellation.

## Tailored resume preview

After tailoring succeeds, **Apply now** always appears above the resume actions. Clicking it rechecks the selected LinkedIn job and resolves its visible, enabled Apply control, waiting briefly if the page is still rendering. An application link opens its URL in a new tab. Button-only controls open the posting's own application flow, including LinkedIn Easy Apply when provided. This action never submits an application. If no Apply control is available, the panel shows an error.

After tailoring succeeds, **Preview resume** opens the latest saved copy inside the panel. The PDF fits the panel width, with zoom controls, page count, **Download PDF**, and **Edit in app**. **Expand preview** widens the existing panel to at most 760px; Back, minimize, close, and navigation restore its normal width. Escape restores an expanded preview first, then returns to the job. **Refresh preview** checks for edits saved in the web app. Downloads use the displayed PDF and stay disabled while a refresh or render is pending.

The web app and extension share `packages/resume-preview`: the viewer, bundled PDF.js worker, render queue, preview state, pinch zoom, and PDF rendering. Trackpad pinching zooms the PDF from 50% to 150%, anchored at the pointer; ordinary two-finger scrolling still scrolls the document. The web adapter feeds its live resume session into the shared provider; the extension supplies the saved document. Downloads and autofill attachments use the resume title with whitespace removed and a `.pdf` extension. Autofill attachments use the same renderer. PDF code loads on demand.

The background worker reads authenticated `GET /api/v1/resumes/{id}/preview` through the shared API. It checks the account, selected job, successful operation, and resume binding before and after the read. Documents stay in the extension panel's memory and are released when preview closes. Only width changes reach the host page. No new extension permission or database migration is needed for preview. Deploy the compatible backend before distributing the updated extension.

Manual acceptance: open a completed LinkedIn job and select **Preview resume**. Check narrow and expanded layouts, multi-page scrolling, text selection, zoom, download, and editing. Save a change in the web editor, return, and refresh. Switch jobs or accounts while loading, minimize and reopen, and try offline loading and retry. Confirm **Apply now** appears immediately on the ready screen, including while LinkedIn is still rendering. Select it and confirm the current job's application opens; a link opens a new tab, while a button uses the posting's own flow. Check LinkedIn Easy Apply and confirm it only opens the flow without submitting. Confirm an unavailable Apply control produces a clear error. Also check that the web editor's live preview and suggestion previews still update.

## Autofill

The design is in `docs/superpowers/specs/2026-10-17-autofill-design.md`, with research notes for Greenhouse (`2026-10-18-autofill-greenhouse-research.md`) and Ashby (`2026-10-17-autofill-ashby-research.md`) in the same folder.

- **Where it runs.** Greenhouse new boards (`form#application-form`) and Ashby have adapters written from the research notes. Neither adapter has fixture tests yet, so both are unverified until a live run. Classic Greenhouse boards (`form#application_form`) use the generic extractor and are unverified. Lever has an adapter based on browser inspection of the Ellevation application on October 22, 2026; its full autofill run and file upload still need manual verification. Workday, SmartRecruiters and iCIMS keep the placeholder. Greenhouse, Ashby, and Lever frames embedded in company career sites use the same adapters. The adapters' host list in `apps/extension/src/autofill/vendors/index.ts` copies these vendors' hosts from `pages.ts`, because the content script cannot load Zod; `test/autofill-hosts.test.ts` checks that the two stay equal.
- **Lever.** Both `jobs.lever.co` and `jobs.eu.lever.co` use `/{org}/{posting UUID}` and `/apply` as one posting identity. Overview pages offer **Open the application form**. The adapter reads `form#application-form`, question labels and required markers from `.application-question`, and section headings, without including dropdown options in labels. Native controls cover contact details, links, custom questions, surveys, and file inputs. Pronouns include the unnamed Custom toggle in the checkbox group and expose its text field only when shown. Location uses Lever's keyup search trigger and selects a rendered `.dropdown-location` result. Resume/CV is the resume attachment; cover-letter uploads remain manual. Apply with LinkedIn and Submit are never clicked. The Worker must also include the shared `lever` vendor schema before the updated extension can request plans.
- **The content script.** The autofill content script (`autofill.js`) runs in every matching frame, including frames created after an Apply click. It reports the form's structure and whether each field has a value, never the values. It receives only values to write, drafts and the resume file; it holds no token and makes no network requests. Its events are synthetic, so the user's typing (trusted events), **Clear**, or a value it did not write makes a field user-owned. User-owned fields are never written again, except by the user's own **Insert** in Write with AI.
- **Detection and routing.** The service worker selects a live ATS document from `webNavigation.getAllFrames`: the top frame first, then the session's existing document, then a single unambiguous embed. Multiple new embeds do not race to replace the session. Greenhouse recognizes both `/{board}/jobs/{id}` and `/embed/job_app?for={board}&token={id}` as the same posting. Embed scan URLs retain only `for` and `token`, so query-only job changes invalidate the previous scan without storing tracking parameters. Frame navigation triggers a rescan, including history changes that leave the parent's iframe `src` unchanged. Writes target `documentId` and carry the expected posting key. Once the parent host is mounted, it observes hidden or removed embeds and pauses filling while a single matching iframe is hidden. Visibility is unknown when no parent host is available or several sibling frames share the same origin. **Open the application form** navigates inside the selected frame and preserves the embedding parameters. Form-only Greenhouse and Ashby embeds use their document title when no job heading exists.
- **What it never touches.** It never clicks Submit or Next and never sends `Enter`. It never touches "Locate me", Dropbox, Google Drive, "Enter manually", the phone flag picker, or Ashby's "Autofill from resume".
- **Session.** The session lives in `chrome.storage.session` under `autofill:<tabId>`, tied to the posting key. A reload puts back what autofill wrote, including the resume file, into fields that are empty again and that the user does not own, with no new AI pass. The session moves when Chrome replaces the tab and is removed when the tab closes.
- **Selected resume.** **Preview resume** beside the picker opens the selected resume in the same PDF viewer used after tailoring, with zoom, download, refresh, and editing. Back returns to Autofill. A resume tailored for another company shows a notice without a **Use anyway** button; Autofill remains available.
- **Server and quota.** API calls happen in the service worker. Autofill has its own hourly quota of 60, separate from chat: each `infer`, `answer`, `notes.merge` or `generate` call that reaches a model costs one unit, and `plan`, `start` and `notes.undo` are free.
- **Survey questions.** Demographic fields follow the ordinary single-choice and multi-select Jev flow. Saved demographic Profile answers are included as evidence. Unsupported or uncertain choices enter the usual question flow, and replies use the same judge as other choices.
- **Inference sources.** Imported job descriptions, requirements, keywords, company and role metadata never enter autofill AI context, including for legacy `useJob: true` requests. User Notes stay intact, including company-specific facts. The original field labels and help text retain the scope of the question. Profile/resume evidence is compacted without dropping explicit false/zero values, dates, negations or relationships. Short text and verification retrieve evidence per field; unrecognized topics retain all records rather than guessing relevance.
- **Decision flow.** Jev evaluates Notes and structured records in parallel source batches. Compact Profile and resume objects are sent once in `state`. Each field is answered from both objects, preferring an explicit Profile answer; the prompt does not mention Notes or restrict the field to a retrieved path. The `insufficient` choice means neither object contains relevant evidence, and record decisions have no `none` choice. A source question in the same batch names the record each answer came from. A passing answer from either call is used: a choice at 0.8 confidence or above, or a multi-select with an option at 0.6 or above. An unsure or failed call never blocks the other call's passing answer. When the calls disagree, a passing answer beats a weak one; between two of the same strength, Profile beats Notes and Notes beat the resume. If the records answer names no source, the conflict cannot be ranked and the field is asked. A weak choice counts only when neither call passes, and gets one focused verification batch, requiring support at least 0.9 and contradiction at most 0.1; agreement never inflates confidence. Verification evidence also lives in structured state, with both checks referencing it. Short text also uses parallel Notes and Profile/resume calls with the same source priority. A Notes fallback order (`A -> B -> C`) fills a free-text field of that kind with its first entry, such as "How did you find out about this opportunity?". Question wording needs only the remaining fields, without applicant records. Replies remain authoritative and are interpreted directly.
- **Failure handling.** Empty source batches are skipped. Source deadlines reserve time for verification; a failed or late call gives no answer and never blocks the other call's answer. All successful source and verification usage is summed into the existing run. Dev traces include raw Jev requests/responses, the selected source, evidence references and verification probabilities.
- **Panel and privacy.** The panel renders the resume PDF it attaches; the CSP adds `'wasm-unsafe-eval'` for the renderer's WebAssembly. There are no new permissions. Field data is not logged, with one exception for local debugging: a step-by-step trace prints labels, options and values to the consoles of an unpacked build (`src/autofill/debug.ts`, off when Chrome installed the extension from the Web Store) and of the web dev server (`apps/web/src/server/autofill-trace.ts`, on only under `vite dev`). Both print errors as their class only.
